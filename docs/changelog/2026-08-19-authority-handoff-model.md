# Authority Handoff Model — ArgoCD Application/ApplicationSet

## Problem

An ArgoCD Application is simultaneously:
- A managed Kubernetes resource (with its own provenance)
- A lifecycle authority for a different set of resources

This dual role cannot be modeled as a simple parent/root relationship. It requires distinct edge types that preserve both directions without conflating them.

## Authority Chain

```
Terraform
  └── provisions ──► Argo Application
                         └── reconciles ──► Group
                                               └── contains ──► Resources
```

With ApplicationSet:

```
Terraform
  └── provisions ──► ApplicationSet
                         └── generates ──► Application
                                               └── reconciles ──► Group
                                                                     └── contains ──► Resources
```

## Separate Relationship Types

| From | Relationship | To | Meaning |
|------|-------------|----|---------|
| Terraform authority | Provisions | ApplicationSet/Application | How the Argo resource arrived |
| ApplicationSet | Generates | Application | ApplicationSet controls the Application lifecycle |
| Application | Reconciles | Group | Argo Application is the active authority for the deployed group |
| Group | Contains | Resource | Resource is an observed member of the group |
| Resource | structural | Resource | Mounts, selects, binds, references, owns |

The Application is NOT a structural root and should NOT be counted as a member of the group it deploys.

## Contextual Authority

Authority belongs to a relationship, not permanently to a node:

```
Application resource:
  Provisioning authority: Terraform

Deployed group:
  Reconciliation authority: ArgoCD/Application

Application generated by ApplicationSet:
  Lifecycle authority: ArgoCD/ApplicationSet
```

The Application is both:
- A managed Kubernetes resource when viewed **upward** (who created it?)
- An authority descriptor when viewed **downward** (what does it govern?)

No conflict in reporting:

```
Application/argocd/payments
  Provisioned by: Terraform/platform
  Generated by: —
  Reconciliation role: Authority for Group/payments

Group/payments
  Lifecycle authority: ArgoCD/Application/payments
  Reconciliation mode: Continuous
```

## Group Identity

The group has its own identity — does not borrow the Application UID:

```yaml
Group:
  type: Application
  name: payments
  namespace: payments
  authorityRef:
    kind: Application
    namespace: argocd
    name: payments
```

ArgoCD tracking annotations supply authoritative membership evidence. Other grouping evidence (part-of, instance, Helm metadata) corroborates without redefining identity.

Authority changes do not destroy the group:

```
Yesterday: Group/payments ← reconciled by Argo Application
Today:     Group/payments ← provisioned by Terraform directly
```

The group remains `payments`; its authority and provenance changed.

## Janitor Consequences

### Evaluating a group member:

```
Resource
  → member of Group/payments
  → reconciled by Application/payments
  → automated sync enabled
  → NoAction
```

### Evaluating the Application itself:

```
Application/payments
  → provisioned by Terraform
  → not continuously reconciled by Terraform
  → but controls Group/payments
  → destructive impact includes the entire group
```

### If generated by ApplicationSet:

```
Application/payments
  → generated by ApplicationSet/platform-apps
  → active upstream reconciler
  → NoAction
```

## Central Rule

> Provenance explains how a control resource arrived.
> Reconciliation authority explains what that control resource actively governs.
> Group membership explains the resulting operational unit.

These must remain **three separate edge types**.

## Operator Generalization

The same dual-role pattern occurs with operators:

```
Helm release
  → installs Operator CRD and controller
      → operator watches Custom Resource
          → reconciles generated workload group
```

Each layer can have different provenance and authority.

## Implementation Requirements

### New Relationship Types

```go
const (
    Provisions  RelationType = "Provisions"    // how the control resource arrived
    Generates   RelationType = "Generates"     // ApplicationSet → Application
    Reconciles  RelationType = "Reconciles"    // Application → Group
)
```

### Ownership Engine Integration

The ownership engine claim layers already support this:
- `HigherLevelReconciler` — the entity above the lifecycle authority
- `LifecycleAuthority` — the entity declaring resources should exist

ArgoCD Application claiming `LifecycleAuthority` for its managed resources is correct.
ArgoCD Application being `Provisioned` by Terraform is a separate provenance fact.

### Graph Model Changes

1. Application → Group: `Reconciles` edge (not MemberOf or Owns)
2. ApplicationSet → Application: `Generates` edge
3. Application is excluded from the group's member list
4. Group's `authorityRef` points to the Application

### Janitor Safety Walk

```go
func shouldAct(resource, releases, groups) Action {
    group := findGroup(resource)
    if group == nil { return Evaluate }
    
    authority := group.AuthorityRef
    if authority == nil { return Evaluate }
    
    // Check if authority has auto-reconcile
    rel := findRelease(authority)
    if rel != nil && rel.AutoReconcile {
        return ObserveOnly
    }
    
    // Check if authority is generated by active upstream
    upstream := findGenerator(authority)
    if upstream != nil {
        return ObserveOnly
    }
    
    return Evaluate
}
```

### Non-Goals

- This model does not replace the existing ownership engine
- It does not change how resources are classified
- It extends the graph with three new edge types for control-resource relationships
- It informs the janitor safety walk but does not change finding generation

## Implementation Phases

1. Add `Reconciles`, `Generates`, `Provisions` relationship types to the graph
2. When ArgoCD Application CRs are indexed, emit `Reconciles` edges from Application to group members
3. When ApplicationSets are indexed, emit `Generates` edges to their Applications
4. Update janitor safety walk to traverse these edges upward
5. Update `kos describe` to show authority handoff chain
6. Ensure group identity persists across authority changes
